# カロナビ「今日のコーチ (β)」改善設計案

作成: 2026年10月7日（JST）／対象: 社長レビュー用／状態: 設計のみ（アプリ・DBには一切変更を加えていません）

表記ルール: 数値はすべて「出典」か「本番DBへのSELECT集計」か「試作プログラムの実行結果」のどれかです。出典が無い決めごとには **【社内案】**、根拠の無い見込みには **【推測】** と付けています。

---

## 0. 結論（1ページ要約）

1. **いまのロジックは「kcalが残りに一番近い組み合わせ」しか見ていない**ため、量と組み合わせが不自然になる。現行の規則をPythonで再現（実機ではない）し、残り50〜1,500kcalを50kcal刻みで回すと、90案中73案に「1食品300g超」「肉・魚150g超」「野菜なし」などの問題がある。
2. **新ルール**は「残りkcalで区分（間食／軽食／一食ちゃんと／一食しっかり）を決める → 区分ごとに主食・主菜・副菜の品数と1品の量の選択肢を出典で固定 → その中からkcal・栄養バランスが一番よいものを選ぶ」。量は「ごはん150g」「魚60〜120g」など決まった選択肢からしか選べないので、**「肉1kg」は仕組み上出せません**。
3. 試作プログラム（本番DBの実在食品66品）で、**残り−500〜2,000kcalの全域・夜間・ランダム1,000件、合計10,373案を、別に書いた検証プログラムで調べて規則違反0件、提案なし0件**。
4. 食品データは本番DBの成分表2,538品のうち**954品に自動で区分が付き、549品は標準量（1人前）でそのまま使える**。足りないのは **汁物（使える0品）と間食（果物・乳製品以外は0品）**。保存済み食品は本番に0件で区分の欄も無い。
5. 名前の第一候補は **「ほどよしナビ (β)」**（残りを使い切らず“ほどよく”収める設計と一致し、カロナビの「ナビ」とそろう）。
6. 別件（要判断）: 本番DBの `public.food_search_spellings` で行レベルセキュリティ（RLS）が無効になっています（Supabaseの重大警告）。詳細は付録B。今回は何も変更していません。

## 3. 新しい提案ルール

### 3.1 残りkcal別のルール表

R = その時点の残りkcal。目標範囲は「下限〜上限」の間に合計kcalが入ること。**合計が残りを超える案は出しません。**

| 残り R | 区分 | 中身（品数） | 目標範囲 | 根拠 |
|---|---|---|---|---|
| R < 0 | 運動 | 運動を1つ（6章） | — | 現行ロジックを改善 |
| 0 ≦ R < 50 | 今日はここまで | 食事は出さず「今日はちょうどいいところです」と表示 | — | 【社内案】 |
| 50 ≦ R < 250 | 間食 | 果物1品、乳製品1品、またはヨーグルト＋果物（1〜2品） | min(R,200)の70〜100% | 上限200kcalはS1の菓子・嗜好飲料「1日200kcal程度」を援用【社内案】。乳製品150kcal未満・果物100kcal未満はS5 |
| 250 ≦ R < 450 | 軽食 | 主食1＋主菜1（卵・大豆製品、または肉・魚60g）＋任意で副菜1品／乳製品／果物のどれか1つ（2〜3品） | Rの80〜100% | 【社内案】。下限250kcalは、試作の候補で、ルールを満たす「主食1つ＋主菜1つ」の最小が214kcal（玄米ごはん100g 152kcal＋たら（焼き）60g 62kcal）で、250kcal未満に収まるのは主食×主菜の99通り中25通りと少ないため |
| 450 ≦ R < 650 | 一食（ちゃんと） | 主食1＋主菜1（または卵と大豆製品の2品）＋副菜2品（計140g）＋任意で乳製品か果物1つ（4〜6品） | Rの80〜100% | S5の650kcal未満、S6の「ちゃんと」450〜650kcal未満 |
| R ≧ 650 | 一食（しっかり） | 主食1＋主菜1（卵と大豆製品の2品、または肉・魚90〜120gに冷奴・納豆・ゆで卵1個を足すのも可）＋副菜2品＋任意で乳製品か果物1つ（4〜6品） | min(R,850)の80〜100% | S5の650〜850kcal、S6の「しっかり」650〜850kcal（八訂の場合620〜850kcal） |

- **80〜100%（間食は70〜100%）にする理由**: 提案は素材の値で計算しており、しょうゆ・ドレッシング・油などの調味料が入っていません。残りを使い切る案にすると、実際に食べると超えてしまうため、最大20%の余白を残します【社内案】。
- **残りが850kcalを超えるとき**: 一食分（最大850kcal）だけ提案し、「残りは次の食事で」と表示します【社内案】。残り1,000kcalでも「1,000kcal分を一度に」は出しません。
- **時間帯（端末の時刻）**【社内案】: 残りを今の時刻からとれる食事に分けます（1日の案）。
  - 0:00〜10:59: 朝食・昼食・間食・夕食。0〜4時は日付が変わった直後で今日の目標がまるごと残っているため、夜ではなく朝の扱い（以前は22時〜翌5時を夜として間食だけにしており、1:10に残り2,438kcalで間食しか出なかった）。
  - 11:00〜14:59: 昼食・間食・夕食。
  - 朝・昼の時間帯の間食は昼食と夕食のあいだの1回（乳製品・果物、200kcalまで）。間食の分を先に取り分け、残りを食事の回数で割って1食の上限（850kcalまで）にします。
  - 15:00〜21:59: 夕食だけ（850kcalまで）。埋めきれない分は間食で足さず、「1食は850kcalまでにしています。この案を全部食べると、残りは約○kcalです。」と表示します。
  - 22:00〜23:59: 間食だけ（2つまで、各200kcalまで）。埋めきれない分は「夜遅い時間なので、間食までにしています。残りは無理に食べなくて大丈夫です。」と表示します。

### 3.4 組み合わせのルール（現実的でない案を出さないための制約）

1. 同じ食品を2回入れない。肉・魚は1品まで。卵料理は1品・2個まで。木綿と絹ごしを同時に出さない【社内案】。
2. 副菜2品は別の食品で、**1品以上は緑黄色野菜**（S5「緑黄色野菜を含む2種類以上」、一覧はS9）。いも・かぼちゃ・とうもろこしは1品まで、トマトとミニトマトは同時に出さない【社内案】。
3. パン・麺に焼き魚・刺身は合わせない【社内案】。
4. 間食の2品の組み合わせは「ヨーグルト＋果物」だけ【社内案】。菓子は1回量のデータを整えるまで出さない（4.3節）。
5. 直近3日に記録した主菜・副菜・果物は出さない。**主食（ごはん等）は除外しない**。候補が無くなったら除外を外して出す。
6. 量は3.2節の選択肢以外を作らない。いまのような「残りに合わせて単位を最大8倍まで増やす」はやめる。

### 3.5 並べ方（上のルールを全部満たした案の中での順位）

点数が小さいほど上位。

| 要素 | 内容 | 根拠 |
|---|---|---|
| kcal | 目標範囲の真ん中（例: 残り450なら405kcal）からの離れ具合 | 【社内案】 |
| PFC比 | たんぱく質13〜20%、脂質20〜30%、炭水化物50〜65%から外れた分。PFCは4・9・4kcal/gで換算し3つの合計を100%とする | S6（比率の換算方法は【社内案】） |
| 主菜のたんぱく質 | ちゃんと10〜17g、しっかり17〜28gから外れた分 | S5 |

## 4. 食品データ：区分フラグと1人前

### 4.1 区分の付け方（定番＝成分表 `official_foods`）

- **自動**: 成分表の食品群コード（01穀類、06野菜、10魚介、11肉 など）と食品名の語（「ゆで」「焼き」「生」「漬」など）で、主食／主菜／副菜／汁物／乳製品／果物／間食／対象外に振り分ける。生の肉・魚、干物の素材、内臓、調味料、油、粉類、ジュース、漬物などは「対象外」。
- **1人前（標準量）の決め方**は3種類:
    - **出典**: S2のSV早見表かS1・S5・S6の数値をそのまま使えるもの（例: ご飯150g、副菜70g、肉・魚80g＝S6の範囲60〜120gの中）。

- **「標準量で上限内」**: 1人前で、3.3節の「しっかり」側の単品上限（主食400・主菜300・副菜150・乳製品150・果物100kcal未満）に収まり、主菜はたんぱく質4.0g以上、主食は炭水化物26.7g以上のもの。4.0gと26.7gは、S1の1つ分（6g・40g）の2/3（S4の「2/3以上で1つ」）。

### 4.4 保存済み食品・公開食品

本番DBの `saved_foods` は現在0件。1回量（`base_amount`・`serving_unit_label`）とkcal・PFCはあるが、**区分の欄と食塩の欄が無い**。

## 6. 運動の提案ルール（残りがマイナスのとき）

### 6.1 いまの動き（`lib/services/daily_coach.dart`）

- 直近30日にやった運動の中から選ぶ。今日の量は「その運動の30日内で一番長い記録の1.5倍まで、かつ45分以内」。
- 運動記録が無い人は「歩くか軽い自重で20分まで」（速歩き: 体重1kgあたり1kmで0.5kcal、時速4.828kmで計算）。
- 45分を超えないと戻せないときは「今日の超過を戻すには、ランニング○kmが必要です。…残りは明日以降の食事で調整しましょう。」（○km＝超過kcal÷体重）。
- 体重が未登録だと距離を出さず、登録ボタンも出さない。

| 100kcal | 3.33km・41.4分 | 今日やるなら、歩くか軽い自重で20分までにします。 | 約48kcal（半分に届かないが、その説明が無い） |
| 200kcal | 6.67km・82.8分 | 今日の超過を戻すには、ランニング3.3kmが必要です。今日やるなら、歩くか軽い自重で20分までにします。残りは明日以降の食事で調整しましょう。 | 約48kcal |

## 7. 名前の案（すべて末尾に「(β)」）

| 案 | 一言の理由 |
|---|---|
| **ほどよしナビ (β)** ★推奨 | 残りを使い切らず80〜100%に“ほどよく”収める設計そのもの。カロナビの「ナビ」とそろい、食事にも運動にも使える |
| ぴったりナビ (β) | 「残りにちょうど合う」が一目で伝わる。ただし実際は残りの80〜100%なので「ぴったり」は言い過ぎになりうる |
| きょうのヒント (β) | 命令ではなく「ヒント」なので押し付けがましくない。何のヒントかは少し伝わりにくい |
| つぎのごはん (β) | 何が出てくるかがすぐ分かる。超過時の運動提案とは合わない |
| あと何たべる？ (β) | 話しかける口調でやわらかい。運動提案と合わず、文字数がやや多い |
| こんだてメモ (β) | 生活感があってやさしい。「メモ」が記録機能と紛らわしい |

推奨は **「ほどよしナビ (β)」**。ひらがな中心でやわらかく、6文字で短く、ルールの考え方（食べ過ぎないところで止める）と名前が一致するため。

## 付録B　別件：Supabaseのセキュリティ警告（要判断・未対応）

- 内容: 本番DB（プロジェクトAYG）の `public.food_search_spellings` テーブルで行レベルセキュリティ（RLS）が無効。Supabaseのアドバイザーが重大（critical）として警告している。RLSが無効だと、公開APIキーでこのテーブルを読み書きできる状態になりうる。
- 直し方の例: `ALTER TABLE "public"."food_search_spellings" ENABLE ROW LEVEL SECURITY;`
- 注意: ポリシー（誰が読めるか）を作らずにRLSだけ有効にすると、アプリからこのテーブルが読めなくなり、検索に影響する可能性がある。読み取り専用のポリシーとセットで入れる必要がある。今回は**何も変更していません**。
